**Time:** 20–30 minutes · **Focus:** implicit interface satisfaction, dependency injection

Go doesn't have an `implements` keyword. A type satisfies an interface when it has the required method set. We'll make our job service depend on a repository contract rather than storage details.

## Interface design

~~~go
type JobRecord struct {
    ID     string
    Status string
}

type JobRepository interface {
    Save(JobRecord) error
    Find(id string) (JobRecord, error)
}

type MemoryRepository struct {
    jobs map[string]JobRecord
}
~~~

With pointer receiver methods `(*MemoryRepository).Save` and `(*MemoryRepository).Find`, `*MemoryRepository` implements `JobRepository` automatically.

## Exercise

Implement a `NewMemoryRepository()` constructor, the two repository methods and this service:

~~~go
type JobService struct { repo JobRepository }

func NewJobService(repo JobRepository) *JobService {
    return &JobService{repo: repo}
}

func (s *JobService) Submit(id string) error {
    // Reject empty ID; store a "queued" job.
    return nil
}
~~~

**Acceptance:** A submitted job can be retrieved with status `queued`. Empty IDs and missing lookups return errors. Use an in-memory repository in tests. Run `go test -v ./...`.

**Hint:** `job, ok := m.jobs[id]` distinguishes a missing key from a zero-value record.

## The typed-nil puzzle

~~~go
var concrete *MemoryRepository = nil
var repo JobRepository = concrete
fmt.Println(concrete == nil) // true
fmt.Println(repo == nil)     // false
~~~

An interface is nil only when both its dynamic type and dynamic value are nil. Constructors accepting an interface may need to guard against typed nils depending on the API contract.

**Stretch:** Inject a fake repository whose `Save` always fails. Verify the service propagates that failure without depending on the fake's concrete type.
