**Time:** 20–30 minutes · **Focus:** value semantics and mutation

Go always passes arguments **by value**. But the value being copied might be a struct, a pointer, or a map header referring to shared data. This matters when our job service changes state.

## Predict before running

~~~go
package main

import "fmt"

type Job struct{ ID, Status string }

func changeValue(j Job) { j.Status = "completed" }
func changePointer(j *Job) { j.Status = "failed" }
func increase(m map[string]int) { m["queued"]++ }

func main() {
    job := Job{"a1", "queued"}
    changeValue(job)
    fmt.Println(job.Status)
    changePointer(&job)
    fmt.Println(job.Status)

    counts := map[string]int{"queued": 1}
    increase(counts)
    fmt.Println(counts["queued"])
}
~~~

Why? `changeValue` mutates its own copy of the struct. `changePointer` follows a pointer to the original. A map argument is itself copied, but still refers to the same underlying map data.

## Exercise: status transitions

~~~go
type StatusCounts map[string]int

func Transition(job *Job, next string, counts StatusCounts) error {
    // Reject nil job, empty status, and nil counts.
    // If status is unchanged: succeed without mutations.
    // Decrement the old status count.
    // Increment the new status count.
    // Update job.Status.

~~~

Start from:

~~~go
job := Job{ID: "a1", Status: "queued"}
counts := StatusCounts{"queued": 2, "failed": 1}
~~~

After `Transition(&job, "completed", counts)`, you should have one queued, one failed and one completed job.

**Acceptance:** Table-driven tests cover a valid transition, a no-op transition, a nil job, an empty next status and a nil map. Invalid requests must leave existing state untouched. Run `go test -v ./...`.

**Hint:** A nil map can be read, but writing to it panics. Validate before mutation.

**Stretch:** Implement an immutable version that returns a new `Job` and cloned counts. Discuss the trade-off between allocation and mutability.
